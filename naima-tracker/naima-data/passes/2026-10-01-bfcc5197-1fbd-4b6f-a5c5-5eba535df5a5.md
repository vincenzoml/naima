naima ui (features/naima-ui-metrics-view-native-window-dashboard, the metrics view in a native window): landed on claude/naima-ui. A new first-party plugin, ui, declares the ui-views extension point and the ui command; the metrics plugin contributes the first view (metric picker, commit range, chart and table, rendered from the records at each request). The server is node:http on 127.0.0.1, a free port, a 48-hex token per run (URL, then an HttpOnly SameSite=Strict cookie). The window is src/plugins/ui/window.ts, a separate Deno process loading jsr:@webview/webview@0.9.0 with permissions scoped to Deno's plug/ cache and GitHub's release hosts; the program itself gets no FFI. The launcher grants ui alone --allow-net=127.0.0.1, read and run of its Deno, and the browser opener, and waits for the program on Ctrl-C. Design decision to review: the window runs out of process because webview_run blocks the main thread, so an in-process server could not answer, and macOS needs the window on the main thread — so the grant is run-deno rather than ffi. Proven: unit and launcher tests on Deno, Node, Bun (293 of 293 each); a real run on this Mac through the launcher (webview user agent fetched /view/metrics, 200; 403 without token; LAN address unanswered; window close ended the launcher). Not verified: a screenshot of the window (macOS refused screen capture to this session); Linux and Windows windows never run; the offline first-run fallback exercised only with a mock. Left: the owner's look test (tests/owner-opens-naima-ui-project-recorded-metrics); closing the feature after it; the lock moves only after merge.
