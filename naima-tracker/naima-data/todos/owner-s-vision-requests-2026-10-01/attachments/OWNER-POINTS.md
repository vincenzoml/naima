# Everything the owner said about what Naima is (2026-09-30 → 2026-10-01)

Each point must appear in the vision, in its own place, with enough weight.

## What Naima is
1. An enabling technology: domain experts who are not remotely coders can build excellent results.
2. For anything that benefits from versioning — software, a scientific data analysis, a paper written with colleagues, several at once in one repository — not only software.
3. Used through an AI agent, a decision support system: it works autonomously when it can; otherwise it helps the owner understand and decide in the owner's own vision and language, without being a technician. A smooth, quiet decision-management system.
4. "The silent company that runs for you": agents do the machine work; the owner only decides. Roles in it (engineering, testing, evidence, release, documentation, publicity/announcements, even business) are in scope.
5. Turning vibe coding into science is ONE example: industry-grade practices and tools used for you, without you knowing them, so results are robust, maintainable, solid.
6. A software-engineering and formal-methods enabler for automated development.
7. You do not need to know git, code, Deno/Node or professional project management; you need an AI agent (and git, which the agent installs if missing). It lives in one folder and never gets in the way.

## What it manages (each needs real treatment, not a mention)
8. Flows — issue management first: report → file → triage → claim → work → prove → close. Reporting from chat, adjusted, or directly as a file by the reporter; filed first, then triaged, by an agent; triage rewrites the description in the agent's own words, comments, links duplicates, sets fields.
9. Planning: epics, features, todos, milestones (a gate with a date), requirements and specifications as items — not just tests.
10. Gates: release gates and what holds them; the queue of what blocks a gate and whose hands it needs.
11. Process management support over the long run: the project keeps going across sessions and agents; session notes; claims; worktrees with a strict naming policy, every worktree carrying a claim.
12. Decisions recorded once and never asked again; permissions that stay settled.
13. Rules: the project's own rules as data (e.g. the owner's working modes), each with its reason; rules that become checks.
14. Evidence and proof: every claim carries evidence; red-then-green tests; proofs that expire when what they proved changes; formal properties tracked like tests, model checkers as verifiers.
15. Metrics (planned): speed, quality, coverage, measured per commit against a baseline, usable as gates, with trends.
16. Structuring a project from the start (planned epic): choosing languages, extreme modularity, separating logic from data.
17. UI design support (planned); referencing skills hosted on GitHub (planned); a dashboard UI (planned, later).
18. Every action an agent takes on an item has a command (description edit and comments planned).

## Principles
19. Privacy: the chat between owner and agent is private; nothing from it is copied into the repository without explicit consent; owner-shared files become attachments only with an explicit yes.
20. Extensible forever, data-only (no OOP), modular; the core does not move; iterate version by version, don't overthink.
21. Plain language; no jargon; Concepts defined once.
